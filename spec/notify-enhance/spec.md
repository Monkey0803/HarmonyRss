# Feature Specification: 通知增强

**Created**: 2026-10-26
**Status**: Draft
**Input**: `TODO.md` P2-1。用户已确认：后台 + 前台都触发；按源开关 + 关键词过滤；免打扰默认 23:00–08:00、每日摘要默认关闭（20:00）；按源分组 + 单条动作（已读/收藏）。

## Overview

把当前「一次聚合通知」升级为可控的通知系统：可按订阅源与关键词筛选，支持免打扰时段与可选每日摘要；
通知按来源分组，单条可标记已读/收藏，点击直达文章。所有策略本地生效，不引入服务端。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按策略决定是否通知 (Priority: P1)

用户订阅了高频源，只希望重要来源与关键词命中时才打扰。

**Why this priority**: 无差别通知是当前最大问题，策略是通知系统的基础。

**Independent Test**: 关闭某源通知、设置关键词后，新文章按预期发/不发。

**Acceptance Scenarios**:

1. **Given** 全局通知开启且某源「通知」设为关闭，**When** 该源抓取到新文章，**Then** 不发送通知。
2. **Given** 关键词列表为「AI, 鸿蒙」，**When** 新文章标题或摘要命中其中之一，**Then** 发送通知；都不命中则不发送。
3. **Given** 文章被规则标记为已读、或被隐藏、或为重复项，**When** 抓取完成，**Then** 不发送通知。
4. **Given** 后台定时抓取与前台手动刷新各产生新文章，**When** 两者先后完成，**Then** 通知按各自批次发送且不重复。

---

### User Story 2 - 免打扰与每日摘要 (Priority: P1)

用户夜间不想被吵醒，但希望白天集中看一次摘要。

**Independent Test**: 在免打扰时段内新文章不弹即时通知；时段结束合并补发；20:00 生成摘要。

**Acceptance Scenarios**:

1. **Given** 免打扰 23:00–08:00 且当前 23:30，**When** 抓取到新文章，**Then** 不发即时通知，进入待通知队列。
2. **Given** 队列中有 3 篇，**When** 免打扰结束（应用回到前台或下次后台任务），**Then** 合并发送一条通知。
3. **Given** 每日摘要开启，**When** 当天首次越过 20:00 且存在当日新文章，**Then** 发送一条摘要通知，且当天不重复发送。
4. **Given** 摘要当天已发送，**When** 再次同步，**Then** 不重复发送。

---

### User Story 3 - 分组、动作与直达 (Priority: P2)

用户看到通知后希望快速处理，而不是先打开应用再找文章。

**Independent Test**: 同一源的多条通知分组展示；单条动作可标记已读/收藏；点击直达文章。

**Acceptance Scenarios**:

1. **Given** 同一源一次新增 3 篇，**When** 发送通知，**Then** 3 条通知按该源分组，可展开查看。
2. **Given** 用户在某条通知上点「标记已读」，**When** 动作执行，**Then** 该文章在应用内变为已读，未读数减 1。
3. **Given** 用户点「收藏」，**When** 动作执行，**Then** 该文章被收藏（并进入远端同步队列，如已连接）。
4. **Given** 用户点击通知主体，**When** 应用启动/回到前台，**Then** 直达该文章详情。
5. **Given** 系统通知权限被拒绝，**When** 用户开启通知，**Then** 显示未授权状态与引导，不崩溃、不反复弹窗。

---

### Edge Cases

- 免打扰时段跨午夜（23:00–08:00）与起止相同（视为关闭）。
- 时区/系统时间变化导致摘要重复或漏发。
- 一次抓取新增文章很多（>50）：通知条数需要上限与聚合，避免刷屏。
- 同一文章多次同步（重复入库）不重复通知。
- 关键词包含空格/大小写/全角半角。
- 通知动作执行时文章已被删除或清理 → 静默跳过。
- 通知权限在系统设置中被关闭 → 设置页显示状态，抓取不报错。
- 应用在前台时收到新文章（前台刷新）→ 仍按策略发送系统通知（用户已选择）。
- 通知队列长时间未清（应用多日未打开）→ 下次打开合并为一条，限制长度。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在后台抓取与前台刷新两条路径上执行同一套通知策略。
- **FR-002**: 系统 MUST 支持按源通知开关（复用现有单源 notify 设置：开/关/跟随全局）。
- **FR-003**: 系统 MUST 支持全局关键词列表（标题/摘要包含匹配，大小写不敏感，任一命中即通过）。
- **FR-004**: 通知 MUST 排除已读、隐藏、跨源重复项以及被规则标记为已读的文章。
- **FR-005**: 系统 MUST 支持免打扰时段（默认 23:00–08:00，可关闭/修改），时段内不发送即时通知。
- **FR-006**: 免打扰期间的新文章 MUST 进入待通知队列，在时段结束后合并发送一条通知。
- **FR-007**: 系统 MUST 支持每日摘要（默认关闭；开启后默认 20:00），每天最多发送一次。
- **FR-008**: 同一次发送 MUST 有通知条数上限（每源最多 3 条，总上限 10 条），超出部分合并为「还有 N 篇」。
- **FR-009**: 通知 MUST 按来源分组（同一源的条目共享 group），支持系统展开。
- **FR-010**: 单条通知 MUST 提供「标记已读」与「收藏」动作；动作执行后更新本地状态并入队远端同步（如已连接）。
- **FR-011**: 点击通知 MUST 直达对应文章详情；应用未运行时冷启动同样生效。
- **FR-012**: 设置页 MUST 展示通知授权状态，并提供开启/授权引导；拒绝后不重复弹窗。
- **FR-013**: 所有通知策略 MUST 持久化并在重启后生效。
- **FR-014**: 新增界面与通知文案 MUST 提供简体中文与英文。

### Key Entities *(include if feature involves data)*

- **通知策略（NotifyPolicy）**：全局开关、免打扰（开关/起止时间）、摘要（开关/时间）、关键词列表。
- **待通知队列（NotifyQueue）**：文章 id、feedId、时间、原因（免打扰/摘要）。
- **通知分组（NotifyGroup）**：按 feedId 分组，成员文章与 actions。
- **摘要状态（DigestState）**：最近一次摘要日期与条数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 关闭某源通知后，该源新文章通知数为 0。
- **SC-002**: 关键词过滤命中/不命中判断准确率 100%（固定用例）。
- **SC-003**: 免打扰时段内即时通知数为 0；时段结束后补发成功率 100%。
- **SC-004**: 每日摘要每天最多 1 条。
- **SC-005**: 单次抓取 100 篇时通知总数 ≤ 10 条（含聚合条）。
- **SC-006**: 通知动作执行后本地状态 100% 同步，已连接账号时进入待同步队列。
- **SC-007**: 点击通知冷启动直达文章成功率 100%。
- **SC-008**: 权限被拒绝时应用可正常抓取与阅读，无崩溃。

## Assumptions

- 通知只覆盖「新入库且仍为未读」的文章；已读/隐藏/重复项不通知。
- 关键词只匹配标题与摘要（不扫正文，避免入库耗时）。
- 免打扰队列与摘要状态存偏好库（JSON）；应用多日未打开时合并为一条并限长。
- 每日摘要依赖应用回到前台或后台任务触发检查，不保证系统级准点。
- 单源通知复用 P1-3 已有的 per-feed `notify` 设置，不新增重复入口。
- 通知分组依赖系统 NotificationRequest 的 group 能力；不可用时降级为单条聚合通知。
- 现有纯状态管理 V2、HDS 约束继续有效。
