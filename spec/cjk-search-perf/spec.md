# Feature Specification: 中文检索性能与分词正确性

**Created**: 2026-10-21
**Status**: Draft
**Input**: 用户要求继续处理「中文检索性能」。上一轮 `rss-core-upgrade` 真机验证发现：FTS 建表时 `tokenize='icu zh_CN'` 失败后降级，中文查询可能退化为全表 `LIKE`，存在 1 万篇规模下达不到 300ms 首屏的风险。

## Overview

让中文检索**确定性地走索引**，而不是依赖「ICU 是否恰好生效」或退化为全表扫描：
修正 FTS 分词配置，启动时用真实中文样本探测分词能力；当设备不具备中文分词时，自动维护
中文二元组索引，使单字、双字、多字与中英混合查询都能在万级数据量下保持可接受的首屏耗时。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 修正分词配置并证明中文可检索 (Priority: P1)

用户在中文设备上搜索「鸿蒙」，结果应来自检索索引，而不是全表扫描；应用启动时应能明确知道当前设备的
中文分词能力，而不是靠猜测。

**Why this priority**: 当前代码同时使用了两种互相冲突的配置方式，且没有能力探针，导致无法判断性能瓶颈是否真实存在。

**Independent Test**: 启动日志中出现明确的中文分词能力结论；在已有数据的设备上搜索中文词，命中来自索引路径。

**Acceptance Scenarios**:

1. **Given** 设备支持 ICU 分词，**When** 应用启动并建好索引，**Then** 日志/诊断显示「中文分词可用」，中文查询走索引路径。
2. **Given** 设备不支持 ICU 分词，**When** 应用启动，**Then** 日志/诊断显示「中文分词不可用」，并自动切换到二元组索引路径，不出现功能缺失。
3. **Given** 旧版本已建过不带分词配置的 FTS 表，**When** 升级到新版本，**Then** 不需要用户干预即可重建为正确配置，且不丢已读/收藏。

---

### User Story 2 - 中文查询在万级数据量下走索引 (Priority: P1)

用户有 1 万篇文章，搜索一个正文中的中文词，首屏结果应在 300ms 内出现。

**Why this priority**: 这是本次修复的核心目标；LIKE 全表扫描在万级文本上不可控。

**Independent Test**: 在设备上构造 1 万篇文章，分别测试单字、双字、四字与中英混合查询的首屏耗时。

**Acceptance Scenarios**:

1. **Given** 1 万篇文章，**When** 搜索双字中文词，**Then** 90% 查询首屏 < 300ms。
2. **Given** 1 万篇文章，**When** 搜索单字中文词，**Then** 能在可接受时间内返回结果（< 500ms）且不漏命中。
3. **Given** 1 万篇文章，**When** 搜索四字中文词，**Then** 结果准确（不因二元组切分产生明显误召回）。
4. **Given** 中英混合查询（如「AI 鸿蒙」），**When** 执行搜索，**Then** 两类词都能命中同一批结果。

---

### User Story 3 - 查询正确性不下降 (Priority: P2)

修复性能不能牺牲正确性：短语、单字、跨标点、大小写、特殊字符都不应报错或漏召回。

**Why this priority**: 检索是核心路径，任何回归都会直接影响可用性。

**Independent Test**: 用固定语料与查询集回归：短语、单字、纯英文、中英混合、含引号/百分号/下划线。

**Acceptance Scenarios**:

1. **Given** 正文包含「鸿蒙系统开发」，**When** 搜索「鸿蒙开发」，**Then** 能命中（允许二元组近似召回）。
2. **Given** 正文包含「HarmonyOS 开发」，**When** 搜索「harmonyos」，**Then** 大小写不敏感命中。
3. **Given** 查询包含 `"`、`%`、`_`、`*`，**When** 执行搜索，**Then** 不抛错、不注入，返回合理结果。
4. **Given** 查询只有空格或只有语法标记，**When** 执行搜索，**Then** 给出空查询引导，不执行全表扫描。

---

### Edge Cases

- 文章正文为空、只有标题时，仍可被标题检索命中。
- 文章在索引构建期间被新增/删除/清理，索引与主表必须最终一致。
- 索引构建中断（应用被杀）后，下次启动能继续或重建，不产生重复行。
- 迁移或索引构建失败时，应用仍可正常启动与阅读，搜索降级但不崩溃。
- 单字查询（如「鸿」）不能因为二元组索引而漏召回。
- 繁体/日文/韩文与中文混排时，索引与查询行为一致。
- 索引体积增长不应导致明显启动变慢或存储告警。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 只使用一种与官方一致的分词配置方式，移除会失败的建表分词子句。
- **FR-002**: 系统 MUST 在启动时探测当前设备的中文分词能力，并将结论暴露到日志与可诊断状态。
- **FR-003**: 系统 MUST 在中文分词不可用（或不可确认）时，自动维护中文二元组索引。
- **FR-004**: 中文二元组索引 MUST 覆盖标题、摘要、正文纯文本，并同时支持单字查询。
- **FR-005**: 系统 MUST 将单字、双字、多字中文查询转换为索引可执行的查询，而不是全表扫描。
- **FR-006**: 多字中文查询 MUST 做候选复核，避免二元组近似造成明显误召回。
- **FR-007**: 中英混合查询 MUST 同时应用英文分词与中文索引策略。
- **FR-008**: 索引 MUST 与文章的新增、更新（正文提取完成）、删除、清理、恢复保持同步。
- **FR-009**: 系统 MUST 支持索引重建，并在升级后自动触发一次（后台、分批、可中断续建）。
- **FR-010**: 检索 MUST 保持现有过滤语法（来源、已读/收藏/稍后读、时间范围）与分页能力。
- **FR-011**: 检索 MUST 在失败时降级为可用路径，且不阻塞阅读与抓取。
- **FR-012**: 系统 MUST 提供可量化的性能验证手段（至少覆盖单字/双字/四字/混合查询）。
- **FR-013**: 所有新增诊断文案 MUST 提供简体中文与英文。

### Key Entities *(include if feature involves data)*

- **分词能力（Tokenizer Capability）**：当前设备是否支持中文分词的结论与依据。
- **中文索引（CJK Index）**：由标题/摘要/正文纯文本生成的字与二元组检索结构。
- **索引状态（Index State）**：是否就绪、已索引条数、最近一次重建结果。
- **查询计划（Query Plan）**：一次查询选择的主路径（FTS / CJK 索引 / 降级）与耗时。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1 万篇文章下，双字中文查询 90% 首屏 < 300ms。
- **SC-002**: 1 万篇文章下，单字中文查询 90% 首屏 < 500ms。
- **SC-003**: 中文查询的索引命中率（走索引而非全表 LIKE 的比例）≥ 95%。
- **SC-004**: 固定查询集（单字/双字/四字/短语/中英混合/特殊字符）正确性回归 100% 通过。
- **SC-005**: 升级到新版本后，索引自动重建成功率 ≥ 99%，且不影响冷启动可交互时间（< 3s）。
- **SC-006**: 索引重建与日常写入后，索引条数与主表条数一致（允许重建窗口内差异）。

## Assumptions

- 官方推荐路径是 `StoreConfig.tokenizer`；FTS 建表不再自定义 `tokenize` 子句。
- 中文二元组索引在同一 SQLite 库内实现，不引入外部分词库或动态库。
- 单字与双字索引以「字 + 二元组」同时入索引，接受索引体积约为正文的 1–2 倍。
- 多字查询允许近似召回，但必须在返回前做子串复核以消除误召回。
- 现有搜索页、查询语法、分页与历史行为保持不变。
- 索引构建在后台分批执行，允许跨启动续建。

## Open Questions

- 无关键未决项。若实测索引体积超出预期，可在实现阶段把正文索引限制为前 N 千字符（默认不限制）。
